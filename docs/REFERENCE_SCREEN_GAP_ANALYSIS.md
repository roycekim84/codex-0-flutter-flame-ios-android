# 참고 화면 기반 프로토타입 갭 분석

작성일: 2026-08-21

## 1. 분석 대상과 결론

첨부된 참고 이미지는 특정 원작의 그래픽을 복제할 대상이 아니라, 다음 요소를 갖춘 세로형 고전 군주제 전략게임의 화면 설계 참고자료로 사용한다.

- 시작부터 통일까지 이어지는 화면 흐름
- 지역·세력·장수·명령을 한 화면에서 빠르게 비교하는 정보 밀도
- 월 단위 플레이와 명령 결과의 명확한 피드백
- 내정·인사·군사·외교·첩보가 별도 화면이지만 하나의 GameState를 공유하는 구조
- 전술 전투와 전투 전후 처리를 분리하는 구조

현재 프로젝트는 지도, 일부 내정, 단순 출병과 전투 화면까지 연결된 기술 수직 슬라이스다. 참고 화면과 비교하면 아직 “완성도가 낮은 UI”가 아니라 “게임의 중간 상태와 명령 모델이 부족한 상태”다. 따라서 다음 단계는 색상·장식 개선보다 데이터와 명령 흐름을 먼저 완성해야 한다.

## 3. 현재 구현과의 차이

현재 흐름은 `세력 선택 → 지도 → 지역 선택 → 개발/징병/이동/출병 → 턴 종료`다. 목표 흐름은 `타이틀 → 시나리오 → 군주 선택 → 월 시작 보고 → 지역/장수 선택 → 명령 배정 → AI 명령 → 전쟁/전투 → 포로/결과 → 월말 보고 → 자동 저장 → 다음 달`이다.

| 영역 | 현재 상태 | 목표 상태 | 우선도 |
|---|---|---|---|
| 시나리오 | 코드에서 가상 데이터 생성 | JSON 데이터팩 선택·검증 | P0 |
| 군주 선택 | 세력 버튼만 존재 | 군주 정보·난이도·영토·장수 비교 | P0 |
| 지역 | 토지·민심·병력 일부 | 금·군량·인구·개발·치수·성벽·무기·군마·태수 | P0 |
| 장수 | 능력치 목록 표시 | 명령 수행자, 소속, 충성, 건강, 상태, 관계 사용 | P0 |
| 명령 | 직접 호출 메서드 중심 | 유형화된 GameCommand와 결과 보고 | P0 |
| 명령 횟수 | 사실상 무제한 버튼 | 장수별 월 1명령, 명령 가능 조건 | P0 |
| 내정 | 일부 명령 | 수행 장수 능력치와 민심을 수식에 반영 | P0 |
| 인사 | 장수 이동만 구현 | 탐색·재야·등용·포상·추방·태수 | P0 |
| 군사 | 단순 출병 | 병력 이동·편성·군량·총대장·지원군 | P0 |
| 전투 | 단순 공격/퇴각 | 부대·지형·이동·공격·화공·돌격·정보·일수·군량 | P0 |
| 포로 | 없음 | 등용·석방·처형·포로 상태 | P1 |
| 외교 | 없음 | 관계 수치·동맹·선물·협박·공동 공격 | P1 |
| 첩보 | 없음 | 잠입·이간·유언비어·매수·정보 제한 | P1 |
| AI | 단순 병력 증가 | 같은 Command API를 사용하는 우선순위 AI | P0 |
| 월말 | 수입과 월 증가 | 수입·유지비·충성·민심·시장·이벤트·보고·저장 | P0 |

## 4. 구현 방향

### 4.1 명령 중심 아키텍처

UI에서 `engine.develop()` 같은 메서드를 직접 호출하는 방식을 줄이고 모든 행동을 명령 객체로 통일한다.

```text
Flutter Screen
  ↓ dispatch(GameCommand)
CommandEngine
  ↓ validate → apply → emit GameEvent
GameState
  ↓
CommandResult / MonthlyReport / BattleResult
  ↓
UI + GameLog + SaveRepository
```

필수 타입:

- `GameCommand`: Develop, Irrigate, Tax, Relief, Search, Recruit, Reward, Dismiss, AppointGovernor, Train, Levy, MoveOfficer, MoveArmy, PrepareWar, Diplomacy, Espionage, EndMonth
- `CommandResult`: 성공/실패, 비용, 변화 수치, 로그 문구, 후속 선택지
- `GameEvent`: 발견, 등용, 질병, 홍수, 전쟁, 포로, 멸망, 통일
- `MonthlyReport`: 세력별 수입·지출·병력·민심·이벤트 변화
- `InfoVisibility`: 공개 정보·인접 정보·첩보로 공개된 정보와 만료 시점

### 4.2 월간 명령 시스템

각 플레이어 장수는 한 달에 기본 1개의 주요 명령을 수행한다. 군주·태수·특수 trait는 예외 규칙으로 데이터화한다.

```text
월 시작 → 명령 가능한 장수/지역 표시 → 장수 선택
→ 명령 선택 → 비용·성공률·결과 미리보기 → 확정
→ 남은 장수 확인 → 턴 종료
```

명령 미리보기에는 수행 장수, 비용, 예상 성공률 또는 변화, 대상, 실패 위험, 실행 후 로그를 표시한다.

### 4.3 지역 상세 화면

지역 상세를 전략 플레이의 중심 화면으로 만든다. 상단에는 지역명·태수·소유 세력·금·군량·인구·민심·개발·치수·성벽·병력을, 중앙에는 지역 장수의 병력·충성도·상태를, 하단에는 내정·군사·인사·이동·정보·턴 종료를 표시한다. 적 지역은 정보 수준에 따라 `????`를 표시하고 공개 기간을 저장한다.

### 4.4 전쟁과 전투

출병은 즉시 전투가 아니라 출병 준비를 거친다.

```text
적 지역 선택 → 출발지 → 총대장 → 장수별 병력 → 군량·금·지원군
→ 예상 전투일·보급 위험 → 출병 확정 → BattleState
```

BattleState에는 부대별 장수·병력·사기·훈련·무기·군마·위치, 지형·이동 비용·방어 보정, 전투 일수·화재, 군량 잔량, 포로·사망·도주 후보를 담는다. Flame은 이를 렌더링하고 계산은 BattleEngine이 담당한다.

## 5. 구현 순서와 완료 기준

### Phase A — 전략 화면

타이틀, 시나리오 선택, 군주 선택, 월 시작 보고, 세계 지도, 지역 상세, 장수 상세를 만든다. 새 게임을 시작해 장수를 선택하고 월간 명령을 배정할 수 있어야 한다.

### Phase B — 명령과 월말

내정, 탐색, 등용, 병력 이동, 월말 요약, 자동 저장을 만든다. 전쟁 없이 24개월 진행해도 음수 자원·중복 장수·고아 지역이 없어야 한다.

### Phase C — 전쟁 수직 슬라이스

출병 준비, 3~5개 부대 편성, Square Grid 전투, 이동·공격·대기·퇴각, 전투 결과, 포로 처리를 만든다. 출병부터 영토·포로·월말 보고까지 한 번의 전쟁이 끊김 없이 끝나야 한다.

### Phase D — 고전 전략 감각

외교, 첩보, 정보 제한, AI 우선순위, 랜덤 이벤트, 세력 멸망·통일을 만든다. 플레이어가 내정·인사·외교·전쟁 중 선택을 고민해야 한다.

## 6. 시각적 구현 원칙

참고 이미지의 정보 밀도와 어두운 지도·목재·청동 분위기를 독자적인 스타일로 재해석한다. 카드 남발 대신 패널·목록·작은 아이콘을 사용하고, 핵심 버튼은 하단에 고정한다. 초상화·지도·아이콘·폰트는 새로 제작한 독자 에셋을 사용한다.

## 7. 완료 체크리스트

- [ ] 타이틀에서 저장 슬롯을 선택한다.
- [ ] 시나리오팩을 바꿔도 엔진 코드는 변경하지 않는다.
- [ ] 군주 선택이 플레이어 세력과 시작 상태를 바꾼다.
- [ ] 지역 상세에서 수치·태수·장수·명령을 확인한다.
- [ ] 모든 주요 명령이 GameCommand·GameLog·SaveState를 남긴다.
- [ ] WAR/INT/CHA가 서로 다른 명령 결과에 영향을 준다.
- [ ] 탐색·등용·포상·추방·태수 임명이 실제 상태를 바꾼다.
- [ ] 출병 전에 장수별 병력과 군량을 편성한다.
- [ ] 전투에서 이동·공격·화공·돌격·퇴각과 지형 보정이 작동한다.
- [ ] 승패 후 포로·영토·병력·로그가 일관되게 갱신된다.
- [ ] 외교·첩보로 관계와 공개 정보가 바뀐다.
- [ ] 월말 요약에서 한 달의 변화가 읽기 쉽게 보인다.
- [ ] AI는 플레이어와 같은 명령 API만 사용한다.

## 8. 현재 버전의 정직한 평가

현재 공개 버전은 Phase A의 일부와 Phase C의 아주 얕은 전투 시연만 충족한다. 다음 구현 목표는 화면 장식이 아니라 Phase A~B의 명령 시스템과 지역 상세를 완성하는 것이다.
